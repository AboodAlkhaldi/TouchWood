# The owner's flagged list: seven specs

The owner's list of 2026-11-17 (the shop's look, policies, projects, videos, emails, Odoo, an admin search),
investigated read-only and answered in three rounds on 2026-11-17 and 2026-11-18. This document holds the seven
specs those answers need, in one round: **every answer, every builder's pick and every question together**, so
the owner accepts once and the build then runs without stopping (memory: screens spec method).

**State:** draft, 2026-11-18. **Not accepted.** Points marked **[PROPOSED Fn]** are the builder's picks; points
marked **[Qn]** are questions. Both are listed again in §9 and §10. Every other point is the owner's answer.
Nothing here is built.

**After acceptance** each part is written into its module's document as an amendment (§11), and the build
follows the plan in `.claude/resume/10-plan-owner-flags.md` (not in the repository): one PR per spec, the shop
specs (S1-S4) one after another, after PRs #395-#397 are merged.

**Sources:** the code on `feat/shop-cart-orders` (PR C, the newest shop code), read on 2026-11-18; the design
export `docs/design/v2/TouchWood Screens.dc.html`; the owner's photo of the specifications table (2026-11-17);
Geist's Theme Switcher page and shadcn's dark-mode and Chart pages, read 2026-11-18.

The dashboard is not here: it has its own accepted spec, `dashboard.md` (PR #398).

## S3 · Policy pages

**Now:** no policy exists. Content's pages (`content.pages`, `Document` with kind `PAGE`) belong to **one store
each** (`store_id`; slug unique per store and language, `pt_slug_unique`). The sign-up box "I accept the terms of
sale and the privacy policy." (`Register.tsx:191-205`, `access::auth.terms_accept`) links to nothing; the customer
keeps a typed version string (`access.customer.terms_version`, default "2026-01"). **Checkout has no terms tick**
and the place-order call carries only the quote (`ShopCheckoutController.php:75-86`). No setting points at a
policy.

**Owner:** each policy is **its own page**; **one text can serve several stores** (KSA and Egypt the same, UAE its
own); **staff type the texts in the panel** with formatted text; **checkout is blocked without terms**; **the
terms box must be ticked**.

### S3.1 What a policy is

- **A new kind of Content document, Policy**, beside pages, posts and projects, with **its own list of stores**
  instead of one store.
- **Each policy has a kind** from a fixed list, so the shop knows which one is the terms **[Q1]**:

  | Kind | Arabic | Where it is used |
  |---|---|---|
  | Terms and Conditions | الشروط والأحكام | **Required for checkout**; sign-up; footer |
  | Privacy Policy (cookies included) | سياسة الخصوصية | Sign-up; footer |
  | Returns and Refunds | سياسة الاستبدال والاسترجاع | Checkout's tick; footer |
  | Shipping and Delivery | الشحن والتوصيل | Footer |
  | Warranty | الضمان | Footer |
  | Payment Methods | طرق الدفع | Footer |
  | Complaints | الشكاوى | Footer |
  | Company Terms | شروط الشركات | Company applications (Q2); footer |
  | Other | أخرى | Footer |

  (The legally expected ones in KSA are from law-firm summaries of the 2019 E-Commerce Law, not the official text:
  a lawyer should confirm them.)
- **A store has at most one published policy of each kind** (Other excepted). Publishing a second refuses with
  "KSA already has a published Terms and Conditions: <its title>."
- **Text**: title, slug and body per language, the body in Content's formatted text (§1.2): two heading sizes,
  bold, bullet and numbered lists, links, images, tables, with the live preview; the Translate button as on
  pages; SEO fields as pages.
- **Address**: `/{store}/{locale}/policies/{slug}`, the same slug in every store it serves; a slug unique among
  policies per language. A changed slug forwards as pages do.
- **Draft or Published**; a draft can be deleted, a published one only unpublished, as pages.

### S3.2 Versions

- **Each publish that changes the text raises the policy's version** (1, 2, 3…) and keeps that version's text
  **[PROPOSED F14]**, so the exact text a customer accepted can always be shown to staff.
- The page shows **"Last updated <date>"** under its title **[PROPOSED F15]**.

### S3.3 Checkout

- **A required tick above the Place Order button**: "I have read and agree to the Terms and Conditions and the
  Returns and Refunds policy." Each name is a link that opens the policy in a new tab. With no published Returns
  policy, the sentence names the terms only.
- **The place-order call carries the tick**; the server refuses an order without it ("Tick the box to agree to
  the terms."), whatever the page sent.
- **A store with no published Terms and Conditions cannot take orders**: checkout shows "Orders can't be placed
  until this store's terms are published." in place of the button, and the server refuses `TermsMissing`.
- **The order keeps which terms were accepted**: the policy, its version, and when **[PROPOSED F16]**; staff see
  it on the order's page ("Terms v3, accepted 18 Nov 2026 14:02"), linking to that version's text.
- **The panel warns**: the dashboard's Needs Attention shows "No Terms and Conditions: KSA" for a store that has
  none published **[PROPOSED F17]**.

### S3.4 Sign-up

- The existing sentence names **Terms and Conditions** and **Privacy Policy** as links to the store's published
  ones (new tab). With either missing, its name is plain text.
- **The customer keeps the terms version they accepted** from the policy itself; the typed setting
  `access.customer.terms_version` is retired **[PROPOSED F18]**.

### S3.5 Footer

- **A row of policy links in the footer's bottom line**, beside the copyright: every published policy of the
  store, in the kind order above **[PROPOSED F19]**. The three typed columns stay as they are.

### S3.6 Company applications

- **[Q2]** Should a company's application require ticking the store's Company Terms (when the store has one
  published)?

### S3.7 The panel

- **Content › Policies** (`/admin/content/policies?tab=`): tabs Published, Draft; columns Title · Kind · Stores ·
  Version · Changed · By. **New Policy**: kind, **stores (a checkbox per store the person may edit)**, then title,
  slug, body and SEO per language as pages. Publish / Save Draft / Unpublish / Delete (draft only).
- **Permission**: its own, **`content.policy.manage`**, given through roles as usual **[PROPOSED F20]**. To change
  a policy a person needs it **in every store the policy serves**; a Super Admin always has it.
- Removing a store from a published policy leaves that store without that kind of policy (its checkout then
  blocks for terms): the form says so before saving.

## S6 · The Odoo connection form

**Now:** Provider, Address, Key, Secret. The address must be the account's address alone (`OdooAdapter::address`,
`:129-148`, `ADDRESS_PATH`); the read adds `/json/2/product.product/read` (`:345`). The Secret is required to wire
a store (`WireStoreHandler.php:77`) and must be typed again with a new address (`ChangeConnectionHandler.php:97-110`),
though the Odoo read never uses it: it only signs webhook notices (`NotificationReceiver`). The Notice Address
is always shown on a wired store (`Provider.tsx:301-315`).

**Owner:** the Secret is optional; **the address box takes the full address, path included**.

### S6.1 The address

- **The box takes the API's full address**, e.g. `https://example.odoo.com/json/2/product.product/read`
  (the placeholder), and **the read and the test call exactly what is saved**: the adapter adds nothing.
- **Rules kept**: HTTPS, a real host, never one inside our network, no query or fragment, 500 characters.
- **A path is now required**: an address with none is refused with "Type the API's full address, its path
  included: https://example.odoo.com/json/2/product.product/read." **[PROPOSED F11]**
- **Saved connections without a path** (local and test data only; nothing is live) get Odoo's path added by
  the migration, so they keep working.
- **The Test button proves it**, as today: a call with one id.
- **Another service** answering the same request and answer as Odoo works under the provider "Odoo" by typing
  its address: no code change.

### S6.2 The Secret

- Labelled **"Webhook Secret (optional)"**, with the line "Only for Odoo's webhook. Leave it empty if you don't use
  one."
- **Empty is allowed** when wiring and when changing. Changing with an empty box keeps the stored one, as today.
- **A new address no longer asks the Secret again**; it still asks the Key again (today's rule) **[PROPOSED F12]**.
- **The Notice Address shows only when a secret is stored.**
- The webhook receiver itself is unchanged: it still waits on Odoo's sample messages (sync.md §2.4).

sync.md amendment 4(a) ("the address typed is the account's alone") is reversed.
